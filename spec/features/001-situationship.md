## 1. 需求来源与目标

- 原始来源：2026-09-19 用户提供《SituationSHIT 项目文档》，要求保留范围、不额外扩需求。
- 决策来源：同日用户对三组推荐方案明确答复“确认，你直接用你推荐的方案就好”。D1 争议、D2 签署与资金、D3 记录与隐私均采用推荐项，结果见第 14 节。
- 目标用户：暧昧期、dating 阶段及暂未明确关系定义的两个人。双方共同签署规则、各存资金，通过正常结束或好友争议判断完成结算。
- 交付边界：本次 T002 仅完成设计和验收定义。READY 不表示应用已实现、已部署或已通过真实 Fuji 验收。
- 中文、移动端优先 Web；Avalanche C-Chain，开发验收使用 Fuji 与官方测试 USDC，配置和核对来源见 [生态文档](../ecosystem.md)。

## 2. 概念与固定参数

Situation 有两名参与者 A/B、同一份 commitment、两类资金、三名监督人和当前状态。Recovery Fund 始终属于原持有人；Commitment Bond 正常结束各退，违约时违约方保证金转给另一方。首版仅失联可申诉；见面次数和关系确认只记录、提醒，不触发罚款。

| 项目 | 冻结规则 |
| --- | --- |
| 两类资金 | 双方同类金额相同；每人每类 0.01–1000 USDC（含端点），最多 6 位小数，内部最小单位整数；不四舍五入接受超精度输入 |
| 失联时限 | 整数 1–30 天，默认 7 天；每次正式确认采用协议固定值 |
| 每月至少见面 | 整数 0–31 次，默认 1 次；0 表示不设最低次数 |
| 关系确认频率 | 整数 1–90 天，默认 7 天 |
| 邀请有效期 | 链上创建后 7 天；该时间内 B 签署；A 的创建交易即首次签署 |
| 入金有效期 | B 签署后 7 天；需三位监督人均接受且双方各一次存足，第二笔入金成功时开始关系 |
| 申诉说明窗口 | 失联申诉成功后 48 小时 |
| 监督团投票窗口 | 紧接说明窗口的固定 72 小时；不因迟提交监督团而延长 |
| 失联申诉提交期限 | 正式确认截止后 7 天；期满仍未申诉可由任意地址关闭本次确认，关系继续，资金不动 |
| 敏感数据保留 | 从关系终止时刻起 30 天；未上链的协议草稿从创建起 7 天后删除 |

时间规则：链上统一 Unix 秒，以区块时间判断，1 天 = 86400 秒；UI 按设备时区显示日期，同时显示时区及剩余时间。操作期限 `t <= deadline` 有效；超时操作仅在 `t > deadline` 有效。到期不会自动产生链上交易，页面提示可执行的操作。精确时间、缺席出口和默认值是 T002 为已确认方案补齐的实现约定，不能在后续实现中随意改成不同规则。

## 3. 创建、身份、签署与监督人

1. A 填写三项规则、两类金额、指定 B 钱包和三位监督人。五个地址必须非零且互不相同；监督人顺序固定为 A 好友、B 好友、共同好友。
2. 前端生成带随机盐的完整协议摘要，链下保管协议；A 签署创建交易，创建不可升级的 Situation 合约并绑定协议摘要。生成邀请链接；链接本身不是查看私有协议的授权。
3. B 用指定钱包登录才可查看协议，前端同时核对摘要及链上公开参数。B 调用接受方法签署同一摘要，变为待入金。其他钱包不能抢占 B 身份。
4. 首次链上签署后，任何字段、参与者和监督人均不能修改；需变化时先取消未生效关系，再创建新协议。生效后不能替换监督人。
5. 三名监督人各自明确接受本次监督职责。受邀时只能查看角色、公开参数、投票职责及协议摘要，不能查看见面约定、关系记录或证据。他们可在 B 签署前后接受，但必须在对应邀请/入金期限内；重复接受不重复计数。
6. 双签且三名监督人均接受后，才能入金。监督人未接受不会要求用户先存钱；到期仍未就绪可取消/超时结束。
7. 协议签署使用链上交易的 `msg.sender`、目标合约与协议摘要绑定；链下登录签名不等于签署关系或授权转账。具体结构、方法与重放边界见 [接口与数据](../contracts.md)。

## 4. 入金、取消与正常使用

### 入金与生效

每人先向本 Situation 地址授权精确的两类金额之和，再一次性存入。合约按恢复基金和保证金分别记账，禁止部分入金、重复入金、第三方替存或任意代币替代。授权成功不代表入金成功。余额/授权不足或转账失败整笔回滚，不改变已入金标记。

第二名参与者成功存足时进入 ACTIVE，记 `activatedAt`，持续时间从此开始。生效前任一方可取消；取消或邀请/入金超时，按实际已入金金额各退本人，没有违约方。任意地址可触发超时处理，不能改收款人。所有已生效关系的退出走正常结束、和解或裁决，不提供任意单方提款。

### 日常记录

- 见面：一方登记实际见面日期（不得早于生效日期或晚于服务器当前 UTC 日期），另一方确认后计数；同一关系同一 UTC 日期最多计一次，双方任一方不能自己确认自己的登记。按 UTC 自然月归档，当前月份目标不按首月天数折算；数据只供双方查看。
- 关系确认：一方发起链下“关系确认”，另一方确认后完成；同一时刻只保留一个未完成请求。下次时间 = 最近双方完成时刻 + 协议频率；尚无完成记录时以 activatedAt 为起点。它不同于可触发失联申诉的链上“正式确认”。
- ACTIVE 可登记/确认日常记录；ENDING 或 DISPUTED 只展示历史，不新增日常记录。被拒绝/尚未确认的记录不增加次数，不自动推断违约。
- 待入金时持续时间显示“尚未开始”；终止后用 `terminatedAt - activatedAt` 固定显示，未生效取消显示 0。见面记录和关系确认不影响资金分配。

### 正常结束

任一参与者可提出，状态 ENDING。只有另一参与者确认同一请求编号后才终止关系并结算；发起人可撤回，返回 ACTIVE。无回应时不会自动结束，双方仍可发起/回应正式确认，符合条件时进入失联申诉。再次发起使用新请求编号，旧确认不能生效。

## 5. 正式确认、申诉和好友判断

### 正式确认

ACTIVE 或 ENDING 时任一方可发送，接收方固定为另一参与者。一个 Situation 同时只允许一条未关闭正式确认或一场争议；下一条从新编号开始。

- 截止前（含截止秒）接收方链上回应：记录 `respondedAt`，关闭本次确认，无资金变化，不能据此申诉。
- 截止后回应：仅记 `lateRespondedAt` 作为材料，不清除原来的未及时回应事实，不自动撤销申诉；发送方仍可在申诉提交期限内申请判断。
- 发起方可在尚未申诉时撤回确认，无资金变化。到达申诉提交期限仍未申诉，任意地址可关闭过期确认，解除占位；不认定违约，也不结束关系。
- 没有正式确认、尚未超时、已有及时回应或超过申诉提交期限，均不能发起失联申诉。

### 申诉与材料

有效申诉仅由正式确认发起方提出，被申诉方固定为接收方。进入 DISPUTED 并取消已有的正常结束请求。`appealDeadline = openedAt + 48h`，`voteDeadline = appealDeadline + 72h`。

说明窗口内双方可提交获明确授权的文字/图片证据；被申诉方可回应正式确认（作为迟到材料）、提交说明、提出“接受结束”或反对指控。单方“接受结束”仅提出和解，不意味着承认违约或授权转移其保证金。无材料也可进入投票，不能因拒绝上传私人材料而自动判违约。

说明窗口结束后任一参与者可提交监督团，进入 VOTING，监督人获得本争议最小视图和本次获授权材料。材料在说明窗口末冻结，不能在投票过程中替换；普通回应状态仍按链上记录展示。

### 投票、缺席与和解

- 仅三位已接受的指定监督人可投本争议一票；投后不可改票。选择“构成违约”或“不构成违约”；不设置主席/管理员额外权重。
- 两票违约：立即形成违约结果，按第 6 节分配。
- 两票否决：立即形成未违约结果，各自退款并结束关系。
- `t > voteDeadline` 时，若未裁决，任意地址可触发超时结果：各自退款并结束，不认定任何人违约。即使没有人提交监督团、无人投票或只有一票，该出口均存在；监督团提交时间不能重置计时。
- 说明/投票阶段且未过 voteDeadline、未形成裁决时，双方可对同一和解请求选择“恢复关系”或“各自退款结束”。一方提出、另一方确认；恢复清除本次正式确认/争议占位，返回 ACTIVE，原 activatedAt 不重置；结束则各自退款。单方提出不停止投票、不延长期限。
- 已产生裁决/超时结果后，旧和解、旧结束请求、旧投票、旧回应全部不能改写结果；同块交易以实际执行顺序决定先后。争议中不能通过正常结束接口绕过争议，但可按上述双方和解路径结束。

## 6. 分配、付款与失败恢复

设每人恢复基金 R、保证金 B，双方完整托管额为 `2R + 2B`。

| 结果 | A 应得 | B 应得 | 关系去向 |
| --- | --- | --- | --- |
| 正常结束、和解结束、两票否决、投票超时 | R + B | R + B | 终止 |
| A 违约 | R | R + 2B | 终止 |
| B 违约 | R + 2B | R | 终止 |
| 和解恢复 | 0（继续托管） | 0（继续托管） | ACTIVE |
| 生效前取消/超时 | A 实际存入额 | B 实际存入额 | 取消 |

原始示例 R = 50、B = 20：A 违约时 A 得 50、B 得 90，总额 140；正常结束各 70。恢复基金绝不转给另一方。平台不抽成，Gas 从调用者钱包的测试 AVAX 支付，不扣托管 USDC。

形成终止结果时，合约一次性锁定每方应得额、原因和 `terminatedAt`，进入 SETTLING，并在同一交易尝试向固定原持有人付款。每方付款独立、已付金额单独记录：一方 USDC 转账失败不能撤销有效裁决、不能重付另一方。失败款保持待付，任意地址可重试，但收款人及金额不能更改；没有管理员挪款/换收款人接口。重复重试已付款项不能再付。实现需防止回调重入；不支持因代币限制失败而伪造到账。

全部应付款实际支付成功后进入 ENDED（已生效关系）或 CANCELLED（未生效关系）。零应付额视为无需支付。SETTLING 显示“关系已终止，资金结算中”，明确列出待付项；结束页区分应得/已付，不把单个交易哈希当到账证明。链下敏感数据的 30 天保留期从 terminatedAt 开始，付款重试不能延长它。绕过存款接口直接转入的代币不计为任何人的协议存款，也不增加结算权益，首版不提供额外转入款的找回工具。

## 7. 隐私和证据

- 已确认链上参与者、监督人地址、资产/金额、失联时限、时间、协议承诺、状态、证据承诺和投票/结算结果可公开读取；详情页隐藏只是 UI 简化。
- 完整协议、见面记录、关系确认、申诉说明和证据原文放链下。协议对 A/B 开放；监督人只在本争议进入 VOTING 后看到失联所需摘要与明确授权给本次监督团的材料，不获得其他 commitment 记录或其他争议证据。
- 额外证据提交前展示接收人名单（双方 + 本次三位监督人）和 30 天保留规则，用户主动勾选授权。未勾选则拒绝提交。提交后投票窗口内不能撤回授权或替换证据，以保证判断依据一致；用户可以选择不提交。
- 首版支持 UTF-8 文字（每条至多 4000 字符）及 JPEG/PNG/WebP 图片（每张至多 5 MiB），每方每场争议合计至多 10 条。图片类型按解码结果校验，拒绝 SVG/脚本，重编码去除 EXIF；不主动采集位置、聊天记录或通讯录。用户自行提交的截图同样走明确授权。
- 材料先安全存入链下，用户再将带随机盐的内容承诺登记到本争议；仅链上登记成功且窗口内的材料可展示给监督团。上传成功不等于证据已生效；未登记材料不影响链上裁决。材料读取失败显示“证据暂不可用”，不得显示为空证据已确认。
- 双方可在保留期内查看自己关系的全部本案材料；监督人仅可读取其被指定且已进入监督阶段的案件材料，授权持续到本关系 terminatedAt + 30 天。和解恢复但未终止的关系，其已进入监督阶段案件记录保留到关系最终终止后清理；未进入监督阶段不向监督人披露。
- 到删除时刻起，API 立即禁止读取到期敏感内容；清理任务至多 24 小时内清除数据库内容、附件及缓存。本 Demo 不建立敏感内容的历史备份；重启后必须补执行清理，不能因服务离线无限延长读取。
- 链上历史及收件人已保存副本无法被服务删除。服务端需解密以授权读取，因此不是端到端加密；运维密钥与服务是信任边界，不能宣称运营方技术上无法读取。

## 9. 模块与执行边界

首版保留 SituationFactory、SituationAgreement、SituationVault、DisputeResolution 四种职责，采用 Factory + 每段关系一个 Agreement 的部署方式。Vault/Dispute 为 Agreement 内部模块，不建立额外可越权调用的托管合约；细节见 [架构](../architecture.md) 和 [接口](../contracts.md)。

链下采用 TypeScript/Fastify + SQLite + 非公开附件目录，处理 SIWE 登录、私有协议、双边日常记录与证据授权。链上结算不依赖后端审批或服务器私钥。每个写入动作由调用者钱包签署付 Gas；超时推进和失败付款重试允许任何地址代为触发，不需要引入自动化机器人。

本轮不授权部署或链上写入。T003 锁定具体依赖和运行时版本；T004 需真实 WalletConnect 项目配置与手机；T006 需单独的 Fuji 部署/测试交易授权、测试 AVAX/USDC 和测试账号。这些是实施前置条件，不是未决产品规则。

## 10. 完整状态机

链上枚举和数据定义以 contracts.md 为准；以下是唯一业务转移表，未列出的写入必须拒绝。`I`=INVITED，`F`=FUNDING，`A`=ACTIVE，`E`=ENDING，`D`=DISPUTED，`S`=SETTLING，`X`=ENDED，`C`=CANCELLED。终态 X/C 只读。

| 当前状态 | 动作 / 调用方 | 前置条件 | 新状态及资金结果 |
| --- | --- | --- | --- |
| 不存在 | create / A | 五地址有效，参数合法，摘要未重复 | I；A 已签，0 入金 |
| I | acceptAgreement / 指定 B | 摘要相同，未过邀请截止 | F；记录双签和入金截止 |
| I/F | acceptSupervision / 指定监督人 | 未过本阶段截止，尚未接受 | 状态不变；增加一份职责确认 |
| F | deposit / A 或 B | 三监督人接受，未过截止，本人未存 | 首方仍 F；第二方转 A，记 activatedAt |
| I/F | cancel / 任一参与者 | 尚未激活 | S；锁定原额退款，全部支付后 C；无入金直接 C |
| I/F | expire / 任意地址 | 过本阶段截止 | 同上；原因分别为邀请/入金超时 |
| A | requestEnd / 任一参与者 | 无当前结束请求 | E；不转钱 |
| E | withdrawEnd / 请求发起人 | 请求编号一致 | A；不转钱，不清除已有正式确认 |
| E | confirmEnd / 另一参与者 | 请求编号一致 | S；各自退款，关闭未结正式确认，付款完 X |
| A/E | sendCheck / 任一参与者 | 无未关闭正式确认 | 状态不变；记录本次接收方和截止 |
| A/E | respond / 接收方 | 对应当前确认，未及时回应过 | 及时：关闭确认；迟到：仅记材料；不转钱 |
| A/E | withdrawCheck / 发起方 | 当前确认未进入争议 | 关闭确认，状态和资金不变 |
| A/E | expireCheck / 任意地址 | 过申诉提交截止且未申诉 | 关闭确认，状态和资金不变 |
| A/E | openDispute / 确认发起方 | 已超确认截止，无及时回应，未过申诉提交截止 | D/APPEAL；清除结束请求；不转钱 |
| D/APPEAL | registerEvidence / 任一参与者 | 未过说明截止，每方未达上限 | 状态不变；登记承诺，不转钱 |
| D | respond / 被申诉方 | 对应本案，未裁决，未过投票截止 | 仅记录一次迟到回应，不撤销申诉 |
| D/APPEAL | startVoting / 任一参与者 | 说明截止 < t <= 投票截止 | D/VOTING；材料集合冻结 |
| D/VOTING | vote / 指定监督人 | 未过投票截止，本人未投 | 未达多数仍 D；两票同向立即转 S（违约分配或各退），付款完 X |
| D/APPEAL 或 D/VOTING | proposeResolution / 任一参与者 | 未过投票截止 | 保持 D；创建新和解请求，不停计时 |
| D/APPEAL 或 D/VOTING | confirmResolution / 另一参与者 | 同一请求编号且未过投票截止 | 恢复：A 且原款托管；结束：S 各退，付款完 X |
| D/APPEAL 或 D/VOTING | finalizeTimeout / 任意地址 | t > 投票截止 | S；各退，付款完 X；无需先 startVoting |
| S | retryPayout / 任意地址 | 固定收款人有未付款 | 仅尝试未付项；全付后 X 或 C；失败保持 S |

正式确认历史状态：WAITING → RESPONDED（及时）/WITHDRAWN/EXPIRED/CLAIMED；CLAIMED 与本次争议关联，争议关闭后不再可用于新的申诉。迟到回应是时间字段，不把 WAITING/CLAIMED 改为 RESPONDED。新确认编号递增，不覆写历史。

争议历史状态：APPEAL → VOTING → UPHELD/REJECTED；APPEAL/VOTING 也可转 TIMED_OUT/RESUMED/MUTUAL_END。裁决结果与付款状态分离，S 期间不得再投票或改变裁决。

## 11. MVP 范围

包含：创建、双签、监督人接受、USDC 两类资金托管、日常记录/提醒、正式确认、失联申诉、三人监督、2 / 3 投票、资金分配与付款恢复、正常结束、中文移动端 Web、实现既定隐私所需的最小链下服务。

不包含：AI Agent、DeFi 收益、eERC 隐私金额、线下商户消费、更多 commitment 类型、自建 L1、主网发布。技术上的超时/失败恢复用于完成现有流程，不增设新的惩罚或收益规则。

## 12. 不变量和异常

1. 每段关系最多两次有效存款、每方一次；恢复基金永远只分配原主；有且仅有一个终止分配结果。
2. 已分配总额等于协议有效入金总额；累计已付不超过已分配；正常双签退出之外，只有已确认的争议/取消/超时路径可终止资金托管。
3. 角色以钱包身份及本关系固定名单校验，不使用前端按钮隐藏或链接保密代替权限。
4. 投票、结束、和解、证据均绑定具体关系与当前对象编号；过期请求、其他关系、其他链的签名/请求不能复用。
5. 同块冲突按链上顺序验证最新状态；同一截止时刻的普通动作与超时动作不能同时满足条件；后端日常确认依靠数据库唯一键和事务保证一次计数。
6. 链下服务/RPC 故障时不开放私有数据，不伪造链上成功。后端离线不赋予监督人额外票权，也不改变合约超时与结算规则。
