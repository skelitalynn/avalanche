# 接口与数据约定

状态：业务数据草案，关联 [001 SituationSHIT](features/001-situationship.md)。这里的 contracts 同时涵盖数据契约、应用 API 和智能合约接口；目前没有已实现接口或已部署合约，以下不是冻结的 ABI/API。

## 公共约定

基础方案已确定使用 Fuji C-Chain 与 wagmi + viem，以下公共约定在实现时遵循；业务字段和具体接口仍由 T002 定义：

- Chain ID 在配置中使用整数，JSON-RPC 表示遵循十六进制格式；Fuji 参数见 [生态文档](ecosystem.md)。
- 地址和交易哈希作为字符串传递，调用前校验格式；不能仅凭格式判定链上存在。
- 金额在内部使用最小单位整数；经过 JSON 时使用十进制字符串，避免浮点精度损失。显示时按资产 decimals 转换。
- 链上时间与应用时间的单位必须在字段定义中注明。
- 错误要区分输入错误、钱包拒绝、网络错误和链上执行失败，保留必要的诊断信息。

## 业务数据

以下为需求层数据语义。字段名、编码、时间单位与链上/链下表示由 T002 冻结，未定义的字段不视为实现要求。

| 实体 / 字段 | 类型与单位 | 约束 / 默认值 | 数据来源 |
| --- | --- | --- | --- |
| Situation：参与者、协议、监督人、状态 | 两名参与者；三位监督人；状态枚举待定 | 双方共同确认并签署；身份绑定规则待定 | 双方协议及链上状态 |
| Commitment：失联时限、每月见面次数、关系确认频率 | 时间单位、计数范围待定 | 首版三项；只定义失联争议流程 | 双方共同确认 |
| 资金：各方恢复基金和承诺保证金 | USDC 最小单位整数；JSON 用十进制字符串 | 分参与者、分资金类型记账；金额范围与部分入金规则待定 | 入金回执与托管状态 |
| 正式确认：发起人、接收人、发起/截止时间、回应 | 时间单位与有效回应表示待定 | 先确认、超期且未回应才能申诉；精确截止边界待定 | 正式确认与回应记录 |
| 争议：当事人、类型、关联确认、申诉状态、证据哈希 | 标识与状态编码待定 | 类型首版为失联；不保存敏感证据原文 | 申诉与获授权证据 |
| 投票：争议、监督人、选择、最终结果 | 构成违约 / 不构成违约 | 三名预定监督人，每人一票；两票违约才授权违约结算 | 链上投票 |
| 结算：接收方、两类资金分配、结果 | 地址、最小单位金额、状态 | 恢复基金归本人；正常各退，违约方保证金归另一方；不得重复支付 | 裁决/双方结束确认及结算回执 |
| 敏感证据与额外授权 | 链下表示与权限模型待定 | 默认不向监督人开放；争议最小披露，额外证据主动授权 | 用户提交及授权 |

## 应用 API / 链交互

每个实际接口记录：名称、调用方、输入、输出、错误、是否写入、对应功能 Spec。无后端时只记录链读取和交易方法，不虚设 HTTP API。

| 接口 | 输入 | 输出 | 错误 / 前置条件 | 对应 Spec |
| --- | --- | --- | --- | --- |
| 创建与邀请、双签（方法待定） | 参与者、三项规则、两类金额、三位监督人、双方签署 | Situation 标识、邀请及签署状态 | B 身份绑定、签名格式、协议可变性待定；不得由第三方代签 | AC-001-01 |
| 存入资金（方法待定） | Situation、参与者、两类 USDC 金额 | 入金记录及回执 | 已双签；资产地址、授权方式、部分入金边界待定 | AC-001-02 |
| 正常结束（方法待定） | 提出方及双方结束确认 | 状态、退款结果 | 一方提出不执行最终结算；争议并发规则待定 | AC-001-04 |
| 正式确认、回应、申诉（方法待定） | Situation、确认、回应/申诉信息 | 确认期限、回应及争议状态 | 无正式确认、未超期、已有及时回应时不能失联申诉 | AC-001-05、06 |
| 投票及违约结算（方法待定） | 争议、指定监督人、投票选择 | 票数、裁决及资金结果 | 每人一票；至少两票认定违约；禁止重复支付；交易触发方式待定 | AC-001-07、08、09 |
| 争议材料读取/提交（接口待定） | 调用者身份、争议、必要材料及额外授权 | 权限范围内的最小信息 | 无关账号拒绝；未授权额外证据不披露 | AC-001-10 |

这些是待设计的操作清单，不预设 HTTP 路由或 Solidity 方法签名。完整状态迁移、错误、事件及非违约路径需按 Spec 第 14 节补齐后再用于并行实现。
