# 多人协作操作指南

本项目使用短期任务分支 + PR，不额外维护 develop 分支。开发规则入口是 [AGENTS.md](../AGENTS.md)，进度以 [Roadmap](../spec/roadmap.md) 为准。

以下是团队工作约定，不代表远程已启用分支保护、强制审批或 CI；每次交付时核对实际设置和检查结果，不自动修改这些设置。

## 1. 从自然语言开始

可以直接向编程助手描述需求：

> 我希望用户连接钱包后能看到自己的测试币余额；网络不对时给出提示。

助手先核对现有项目，把需求写入功能 Spec；仅对关键业务缺口提问。例如余额刷新时机未明确时，应记录待定或明确采用的约定，不能悄悄承诺实时刷新。

以下仅为写法示例，并非本项目已批准的功能：

| 原始表达 | 可验证的行为 |
| --- | --- |
| 看自己的余额 | 连接账号 A 后，显示 A 在目标网络上的原生币余额与单位，结果与同一查询的 RPC 返回值一致 |
| 网络不对时提示 | 钱包在非目标网络时显示目标网络提示，不把其他网络的余额展示为目标网络余额 |
| 连接失败也能用 | 用户拒绝连接后保持未连接状态，展示原因，仍可再次发起连接 |

Spec 写清输入、正常/异常/边界行为、AC 和不做事项；Roadmap 再将其拆成连接、读取、错误反馈等可独立验证的任务。小功能可在同一 PR 中交付 Spec、代码和测试。多人依赖同一接口时，先评审接口约定，再分别实现。

## 2. 认领任务与分配编号

1. 查看最新 main、Roadmap 和开放 PR，确认没有重复任务。
2. 在任务中填写负责人（GitHub 用户名）、分支和涉及文件/模块；开始时更新为 DOING。
3. 通过团队已有沟通渠道或 Draft PR 公布认领。仅写在个人本地文档不算完成团队协调。
4. 同一任务只保留一位负责人；需要多人并行时拆成子任务，并约定谁修改公共接口。

新功能使用下一个空闲编号，如 `001-wallet-balance.md`；任务使用 `Txxx`，子任务可使用 `T005-1`。分配前同时检查 main 和开放 PR；发生撞号时，后认领者在合并前改号并同步所有 AC、任务、测试和链接，不复用已合并的编号。

项目负责人已授权助手对完成的仓库修改直接提交、推送、创建 PR 并自行合并；通过 PR 公布任务和验证结果。向他人发送额外消息仍按用户明确授权执行。

## 3. 创建自己的工作分支

先确认当前工作区没有未处理的修改。不同开发者使用各自的 clone；同一机器上的并行会话也要使用不同 clone 或 worktree。

```bash
git status --short
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feat/001-wallet-balance
```

分支名是示例，替换为实际编号与主题。若 pull 无法快进，先检查本地与远程差异，不用 reset 或强推覆盖历史。有未提交修改时先在原任务分支妥善保留，不带到新任务里。

| 类型 | 分支示例 | 用途 |
| --- | --- | --- |
| 功能 | `feat/001-wallet-balance` | 功能及对应 Spec、测试 |
| 修复 | `fix/001-network-check` | 明确的缺陷修复 |
| 文档 | `docs/collaboration-rules` | 文档、规则或仅 Spec 变更 |
| 工程 | `chore/test-setup` | 构建、工具与工程设置 |

## 4. 实现、验证和提交

按 READY 的 Spec 实现对应任务；遇到行为变更先更新 Spec。公共文档只改与本任务有关的段落，不顺手重排整个 Roadmap 或覆盖他人进度。

先执行任务列出的测试，再检查并提交明确的文件：

```bash
git diff --check
git diff
git status --short
```

使用 `git add <具体文件>` 逐项暂存（将占位符替换为真实路径），然后：

```bash
git diff --cached --check
git diff --cached
git commit -m "feat(001): show wallet balance [T005-1]"
git push -u origin HEAD
```

commit 示例应改成实际内容；可用 feat/fix/docs/chore/test 前缀。一次提交尽量表达一个完整意图，避免混入不同任务。

`git diff --check` 只检查差异格式，不代表功能测试通过；未跟踪的新文件需暂存后检查或单独检查。Mock 前台的实际检查命令见根 README；后端与合约命令由 T003 继续补齐。

## 5. PR 与验收

PR 目标分支为 main；一个 PR 围绕一个主题，Spec、代码、测试和必要的进度更新一起检查。按项目负责人已确认的流程，助手完成检查后可自行创建 PR 并合并，无需等待额外的人工确认；如果用户要求队友评审或远程规则要求审批，则满足该要求后再合并。自检与独立队友评审应如实区分。

PR 描述可复制以下结构：

```markdown
目的与结果：解决什么问题，用户会看到什么变化。
Spec / 任务：文件链接、Txxx、对应 AC。
变更范围：主要模块，接口或数据变化。
验证：工作目录、实际命令/步骤、结果、代码版本。
限制：未执行检查、外部阻塞、尚未覆盖的场景。
```

作者负责实现和证据，检查内容包括 Spec 是否可执行、实现是否符合 AC、是否影响他人模块。合并前确认远程 PR 的最新提交与已验证版本一致、可以合并且无未解决冲突；存在 CI 时等待适用检查完成且通过。无 CI 时在 PR 中明确本地执行的检查，不能写“CI 已通过”。合并时绑定已核对的提交 SHA，完成后确认 GitHub 合并状态并同步本地 main。

建议在 GitHub 使用 Squash merge，保留一个主题清晰的主线提交。任务 DONE 表示其约定验收已完成，PR 字段另记“未创建 / 评审中 / 已合并”；不要把未合并任务描述为主线已具备的能力。

完成后将合并 PR 链接记入 Roadmap，可随下一次进度文档 PR 更新。不要为回填当前合并 SHA 制造循环提交。

## 6. 同步主线与处理冲突

在自己的任务分支、工作区干净时执行：

```bash
git fetch origin
git merge origin/main
```

解决冲突时保留双方有效需求和验收记录，按正确的接口关系修改代码。Spec、contracts.md 或任务认领冲突需要和对应负责人对齐；不确定时记录阻塞。解决后暂存具体文件，执行 `git merge --continue`，重跑受影响检查，再推送分支。

若无法安全解决，使用 `git merge --abort` 返回合并前状态，保留任务分支继续协调。共享分支默认用 merge 同步，不强推或改写他人提交。

分支合并后切回 main 并使用 `git pull --ff-only origin main` 更新。确认 PR 已合并、工作区干净且没有未交付内容后再清理分支；Squash merge 后 Git 可能仍认为分支未合并，不盲目强删。

## 7. 交接与阻塞

交接时在任务里留下负责人、分支/PR、已完成 AC、验证结果、未完成事项和下一步。BLOCKED 写明原因、需要谁提供什么、满足什么条件可恢复；解除后回到 DOING 或 VERIFY。

项目负责人以后可按团队需要配置 main 分支保护和 CI；本次文档初始化没有替团队修改 GitHub 设置。
